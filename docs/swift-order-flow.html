Swift Order Flow

How a signed-message ("Swift") order travels from the UI to an on-chain fill — the four services it passes through, who is actually responsible for landing the transaction, and every point where an order can be silently dropped.

1. Overview

A Swift order is a gasless, signed-message order. The user's wallet (or a delegate) signs the order params off-chain; the taker never sends a transaction. Instead, a chain of off-chain services validates, distributes, and finally a keeper/filler submits the on-chain transaction on the taker's behalf. This inverts the usual model: the UI returning 200 OK means the order was accepted for distribution, not that it landed.

The path has four hops between the browser and the blockchain. Understanding which hop owns which responsibility is the key to debugging "the order was accepted but nothing happened on-chain" — the single most common Swift failure mode.

Signed message
The order params (market, direction, size, auction curve) signed by the taker or delegate. Carries a UUID and the slot it was signed at.
swift-server
HTTP endpoint the UI posts to. Verifies the signature, runs an off-chain simulation, and publishes to Redis. Never touches the chain.
swift-ws-server
Subscribes to Redis and re-broadcasts each order to authenticated WebSocket clients (the keepers).
Filler / keeper
Subscribes to the WebSocket, decides whether the order crosses, and builds + sends the on-chain transaction.

2. End-to-end sequence

The round-trip below shows the full lifecycle. Note that the 200 OK the UI receives (step 1's return) happens right after the Redis publish — long before any on-chain activity. Everything from step 4 onward is invisible to the browser.

Two things make this flow surprising. First, the receivers count in the swift-server log (step 2) counts Redis subscribers — i.e. the swift-ws-server — not keepers. receivers=1 means "the ws-server got it," not "a keeper got it." Second, the swift-server's local simulation (step 1 note) is a pre-publish admission check against cached state; it guarantees nothing about on-chain landing.

3. Services & responsibilities

All four services deploy from separate repos but run in the same cluster. On mainnet they are Kubernetes deployments in namespace mainnet-beta, with logs shipped to Loki (query in Grafana by the app label). The keeper exists in two implementations — both subscribe to the same ws-server, and this distinction matters for debugging (see §4–5).

ServiceLoki app labelRole & boundary
swift-server swift-server-app Publisher. Verify sig → simulate → PUBLISH to Redis. Responsibility ends at publish.
swift-ws-server swift-ws-server-app Redis subscriber → WebSocket fan-out to authenticated keepers. Drops if no keeper is subscribed.
Rust filler rust-filler-bot keeprs. Has a place-only fallback — lands non-crossing swift limits as resting orders.
TS filler order-filler-multithreaded-bot keeper-bots-v2. Only sends on a DLOB cross — never places a non-crossing swift order.
The receivers field is a two-hop trap. receivers=1 on swift-server-app proves only that the swift-ws-server-app received the order from Redis. The ws-server then does its own fan-out; if no keeper is WebSocket-subscribed to that market, it logs No receiver found for topic ... dropping order message! and the order dies there — despite the healthy-looking publish upstream.

4. Filler decision logic

Once a keeper receives an order over the WebSocket, it evaluates whether the order crosses resting liquidity or the vAMM, then branches. The Rust filler (rust/keep-rs/src/filler.rs) has three outcomes from evaluate_swift_crosses: Fillable, NotFillable, and Drop. The flowchart below traces the two paths that can reach the chain.

Both on-chain paths (try_swift_fill, try_swift_place) build a transaction and hand it to an async tx worker, which simulates, sends (skip_preflight: true, max_retries: 0), and later confirms. There is no retry: a single sim/send/confirm failure logs and drops the order.

5. Where orders silently die

An order that returns 200 OK at the UI but never lands on-chain died at one of the hops below. They are ordered from earliest (UI-adjacent) to latest (chain-adjacent).

HopFailureSignature in logs
swift-ws-server No keeper WS-subscribed to the market No receiver found for topic ... dropping
ws-server → keeper Keeper pointed at a dead WS host (stale image) No new swift order line on any keeper
filler (TS) Non-crossing swift limit — no place-only path Order cached, never surfaced as a fill node
filler (Rust) Auction/placement window already expired swift order past placement window, not placing
filler → tx Keeper's own subaccount not initialized on-chain filler account: NoAccountData(...) → panic at filler.rs:716
tx worker Simulation / send / confirm failed (no retry) tx_event with status: sim_failed | send_error | confirmation_failed
Observed failure — keeper subaccount not initialized. When a swift order crossed, rust/keep-rs/src/filler.rs at line 716 did .try_get_account::<User>(&filler_subaccount).expect("filler account") on the filler's own trading subaccount, which returned NoAccountData because that account was never created on Velocity. The .expect() panicked the keeper's main thread, Kubernetes restarted it, and the next crossing order crashed it again — a crash loop, so no fill ever landed. The non-crossing (try_swift_place) path hit the same missing account but returns with a warning instead of panicking, so that path failed silently. Fix: initialize the keeper's User subaccount on-chain; harden the fill path to log-and-skip instead of .expect().

6. Log targets & how to trace

The whole keeper tx path logs under one target, filler, plus a structured tx_event JSON line. Crucially, the only line on the send/confirm path that carries the order UUID is the tx_event; the send-success and account-load-failure lines carry the signature or subaccount instead — so a naive |= "<uuid>" grep can dead-end even though the order was processed.

StageLog line (target filler)Level
Receivednew swift order. uuid=...info
Fill pathfound resting cross ... / try fill swift orderinfo
Place pathswift order not fillable yet, placing on-chaininfo
Expiredswift order past placement window, not placingdebug
Sim rejectedsim failed: ...warn
Send failedfill failed 🐢: ...info
Confirm failedtx confirmation failed 🐢: ...info
Outcome (has UUID)tx_event JSON: { "uuid", "sig", "status", "error" }info

Because send/confirm failures log at info (not warn/error), filtering Loki to level>=warn hides them. Trace by time window around the "placing on-chain" line rather than by UUID alone: 

# 1. Find the order and its decision on the keeper (rust-filler-bot)
{app="rust-filler-bot"} |= "<uuid>"

# 2. If it dead-ends after "placing on-chain", widen to the time window
#    (do NOT filter by level — send/confirm failures are info-level)
{app="rust-filler-bot"}     # range: the ~5s after the placement line

# 3. The tx_event line carries the verdict; read its "status" and "error":
#    placed / place_noop_* = landed;  sim_failed | send_error |
#    confirmation_failed | insufficient_funds = failed at that stage

# 4. Upstream sanity check — did a keeper even receive it?
{app="swift-ws-server-app"} |= "<uuid>"   # look for receivers=N or "No receiver found"
